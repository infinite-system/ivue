## Strategy notes

- Put GitHub topics, About metadata, README/social preview, npm metadata, and a first release in place before any directory form; they are shared inputs to most rows.
- Do the seven directory/index checks in one pre-launch or week-1 batch, then leave them alone; they are permanent surfaces, not a posting cadence.
- Use `introducing-ivue` for library listings, `one-kilobyte-feature` for independent size surfaces, and `what-native-signals-should-steal` only where the audience already understands reactivity/signals.
- Open an issue before a PR when a list has no obvious section; this prevents a promotional PR that maintainers must close.
- Submit the free visual galleries only after thumbnail QA of the dark and light homepages; defer paid award sites until free-gallery evidence justifies the fee.
- Treat js-framework-benchmark as an engineering project with a neutral implementation and CI, not as a launch-day link drop.
- Do not cite passive analyzer pages until the public npm release has propagated and the exact import/version has been checked.
- Keep GitHub Collections off the calendar: it has no public editorial route; repository quality is the only available input.
- For roadmap.sh and other curricula, submit a learning resource or guide, never a bare product listing; one rejected proposal is routing data, not a reason to resubmit.
- Schedule OSS-fitting product directories after technical launch signals; generic-directory traffic is lower-intent than Vue/reactivity indexes.
