# Обычный класс снова держит реактивное состояние — в 1,1 kB

ivue — слой классов размером 1,1 kB поверх реактивности Vue. Обычный TypeScript-класс получает реактивное состояние, остаётся объектом и работает в компоненте, Worker или терминальном приложении.

Короткий пример:

```ts
import { Reactive } from 'ivue'
import { ref } from 'vue'

class $Counter {
  get count() {
    return ref(0)
  }
  get double() {
    return this.count.value * 2
  }
  increment() {
    this.count.value++
  }
}

export const Counter = Reactive($Counter)
```

`Reactive()` один раз преобразует prototype. Getter, возвращающий `ref()`, становится состоянием: ячейка создаётся при первом чтении и потом кешируется. Обычный getter остаётся обычным getter-ом. Если он читает реактивное значение внутри эффекта, Vue отслеживает это чтение. Для него не нужен отдельный `computed()` на каждый экземпляр.

Методы связываются лениво и один раз. Поэтому `instance.increment` можно передать обработчику без ручного замыкания. Сам экземпляр остаётся обычным объектом. На этапе создания не запускается скрытая инициализация.

Размер движка — **1,1 kB gzip**, зависимостей нет, покрытие тестами — **100%**. Эти цифры — следствия формы:

- нет proxy на экземпляр;
- нет заранее созданных ячеек для состояния, к которому никто не обращается;
- нет compiler runtime;
- нет отдельной development-реализации, которая отличается от production.

Из этой же формы следуют измерения. Создание экземпляров работает в **55–253 раза быстрее** альтернативных подходов в опубликованном сравнении. Модель может представить **20 000 000 formula-capable cells** по 4,7 байта на ячейку. Отдельный production-кейс — терминальное IDE Invar, которое AI-агенты собрали на ivue. В текущем срезе там около **94 000 строк исходников**, один вызов `computed()` и ноль обходных решений для циклических импортов.

Здесь важен не размер сам по себе. Важен вопрос, который его объясняет: какая часть механики действительно нужна? Если derived value — это только чтение уже существующих сигналов, отдельный узел может быть лишним. Если состояние адресуется по миллионам ключей, сигнал создаётся при наблюдении ключа, а запись в ненаблюдаемый ключ ничего не выделяет. Если класс является общей моделью, компонент не должен владеть его существованием.

Это способ проектирования через проверяемые ограничения. Сначала удаляется предположение: «каждый getter обязан быть computed». Затем остаётся генератор: реактивность появляется там, где есть tracked read. После этого проверяется граница: дорогая работа может получить кеш, но кеш должен иметь измеримую причину.

ivue не отменяет Composition API. `ref()`, `watch()`, lifecycle hooks и composables работают внутри конструктора. Класс добавляет форму поверх этого механизма. Именно поэтому один и тот же объект можно создать в Vue-компоненте, тесте или Worker.

Документация и интерактивные проверки: https://ivue.dev

Проверьте результат на своей модели: сначала измерьте создание и память, затем решите, какие производные значения действительно нужно кешировать. Число без метода не является доказательством.
